# 2Ship / Majora's Mask: transferable host-port boundaries

## Scope

Compare the pinned 2Ship native port with the independently pinned, present-day `zeldaret/mm` decompilation. This is source research and proposed 35mmIsle work contracts, not an implementation, compatibility certification, or permission to copy code. Randomizer, enhancement/mod frameworks, Zelda scene/actor conventions, and Zelda save gameplay are excluded from reuse. No builds, tests, formatters, runtime checks, or gates were run.

**Baseline distinction.** MM describes an N64 US 1.0 decompilation, explicitly not a PC port [B2]. Its Makefile also exposes WIP `n64-jp-1.1`; therefore the README's “only N64 US” statement is narrower than the actual build configuration [B3]. 2Ship's extractor accepts US 1.0 and US GameCube identities and chooses `N64_US` / `GC_US` extraction definitions [A4]. These observations establish supported asset inputs, **not** the precise MM commit from which 2Ship diverged. Historical ancestry was not established by this study; this document must not be read as “2Ship is simply newer decomp.” Renamed symbols, changed headers, and region coverage are differences between these two snapshots, not a chronological change log.

`Observed` below means directly visible in the cited source. `Proposed` means a Snap decision. `[INFERENCE]` marks a conclusion not itself established by an executed experiment.

### 1. Lifecycle and scheduling: replace the platform, retain observable ordering

**Observed paired sources.** MM starts a graph OS thread from `Main`, while 2Ship directly enters its graph loop and leaves original scheduler startup disabled [L1, L2]. MM's `Graph_ThreadEntry` loops until a game state terminates [L3]; 2Ship persists the graph/game-state/overlay pointers in `runFrameContext`, returns after one update, and resumes at `nextFrame` [L5]. This is an explicit native control-flow adaptation, not a wholesale replacement of gameplay with C++.

The retained queue calls are not evidence of a complete N64 scheduler. 2Ship still constructs/submits an `OSScTask`, but executes graphics through the C++ bridge in the same graph path [L5]. Hardware-style metrics also remain: a comment says RDP completion is never called and the port substitutes a frame-time-derived value [L5]. The mature reference therefore contains compatibility remnants, disabled branches, and approximations that 35mmIsle should not copy as its architecture.

**Concrete host boundary.** C keeps `Graph_ProcessGfxCommands(Gfx*)`; C++ owns `Ship::Context`, `Fast3dWindow`, native event handling, rendering, and audio synchronization [L6]. The bridge wakes its audio worker, performs presentation, then waits for `audio.processing` to clear. `DeinitOTR` waits for save work, exits/joins audio, and destroys the context [L7]. These are specific ownership and sequencing patterns, not an API guarantee for a different libultraship pin.

**Snap invariant.** Original `omRunProcess` starts a thread-backed process and waits for its yield message; `omUpdateAll` traverses objects and priority lists in order. `ohWait` yields by posting a message and stopping the current thread repeatedly [N1, N2]. [INFERENCE] A callback-only `RunFrame` transplant or freely concurrent jobs would lose suspended call-stack/local-state semantics. A host frame driver can wrap this behavior only after the Snap process implementation preserves that contract.

### 2. Assets and ABI: serialized values are not host pointers

**Observed paired sources.** MM reads ROM bytes through VROM→ROM/DMA machinery [A2] and resolves segment-number/offset values through `gSegments` [P1]. 2Ship changes the segment conversion macro to identity [P3], widens graphics words [P4], and registers resource importers by format, textual type, numeric type, and schema version [A5]. Thus copying only `uintptr_t` typedefs cannot complete the port: asset references, packed command buffers, structures, offsets, byte order, and loader lifetime must agree at both ends.

`__OTR__` is still a resource signature despite `.o2r` archive filenames: `ResourceMgr_OTRSigCheck` tests the pointed-to bytes for that prefix [P5]. This is a string/reference convention, not a safe universal test for arbitrary numeric segmented addresses. Do not introduce the reference's heuristic into unconverted Snap pointer paths.

The importer example reconstructs an `AudioSequence` from explicit `ReadUInt32`, `ReadChar`, `ReadUByte`, and `ReadUInt16` fields, allocates sequence data, and restores font references [A7]. It does not `memcpy` a ROM object into a host structure. Adopt that serialization boundary; reject its MM sequence/font schema for Snap. Resource ownership must keep native pointers valid while C code or a queued display list consumes them.

**Input/compatibility layers.** 2Ship uses `0x5354631C` / `0xB443EB08` header identities, CRC32C values for accepted full ROM content, region-selected XML/config, archive game-version checks, and separate port-version metadata [A4, A6]. `VerifyArchiveVersion` checks major version for the ROM archive; the port archive compares major/minor/patch [A6]. These are observed policies, not recommendations to reuse those exact compatibility thresholds or hash algorithms. Snap should record a collision-resistant content hash, extraction-definition revision, resource schema version, and region identity separately; reject mismatches before gameplay or save mutation.

### 3. Audio and saves: native I/O does not supply game semantics

**Observed paired audio.** MM constructs `aspMain` tasks from ABI commands, submits scheduler work, and uses AI buffers [U1, U2]. 2Ship's old task updater returns `NULL`; active buffer production performs command-queue work and synthesis [U3]. Its synthesis includes `2s2h/mixer.h` [U4], whose macros replace command emission with calls such as `aLoadBufferImpl`, `aADPCMdecImpl`, and `aResampleImpl` [U5]. CPU mixer state models DMEM and ADPCM/resampling state [U6]. This is the necessary missing middle between gameplay audio commands and the host device.

2Ship initializes device output at 32 kHz; its worker uses 528/560 sample counts, stereo, and `R_UPDATE_RATE` before handing bytes to the PCM sink [A5, U7]. These values embody this port's timing/buffering choices. They are not verified Snap constants, and its synthesis opcode coverage does not prove coverage of Snap's audio ABI. Proposed reuse is the separation of synthesis from output, not the MM mixer implementation or cadence.

**Observed paired saves.** MM FlashRAM code returns transport errors and waits for DMA/page completion [S1]. 2Ship redirects read/write entry points to SaveManager, then makes busy/result checks constant [S3]. The manager uses MM page-to-save mapping, `newCycleSave` / `owlSave`, `2S2H_SAVE`, and migration version 8 [S4, S5]. These are Zelda gameplay/schema assumptions. Its direct `ofstream` write is not an observed atomic durable-write guarantee [S4].

**Proposed Snap contract.** Preserve the authoritative save payload/checksum and game-visible completion/error behavior until a separately justified schema conversion exists. Keep host paths and write ownership outside gameplay; bound reads/writes; write through an atomic replacement/backup strategy with error propagation. Do not persist widened host structs or pointers. Shutdown must wait for actual outstanding writes, not a compatibility API's constant success.

### Graphics and photographic nontransferability

**Advertised backend matrix, not exercised here:** 2Ship documents DirectX 11 on Windows, OpenGL across its platforms, and Metal on macOS, with restart required when changing APIs [B7]. This is product documentation, not evidence that Snap commands or depth readback behave equivalently on those backends. 35mmIsle's backend acceptance matrix must be selected independently.

2Ship's F3DEX2 selection plus `DrawAndRunGraphicsCommands` demonstrates native display-list presentation [B1, L6]; it does not establish Snap microcode support. In authoritative Snap, scoring binds image/current-depth/per-Pokémon/pre-Pokémon buffers, draws copies between individual objects, allocates 64×48 `u16` surfaces, and compares exact depth values with sentinel `0xFFFC` [N3]. Generic color screenshots or point-depth reads cannot alone demonstrate these semantics. A faithful photographic path requires a resolving experiment before importing a renderer path or promising photo/scoring parity.

## Reuse decisions

| Decision | Pattern | Boundary for 35mmIsle |
|---|---|---|
| **Adopt** | C gameplay / C++ host services through explicit C-linkage entry points | Keep the bridge narrow: initialize/shutdown, one authoritative tick, display-list submission, input snapshot, resource access, PCM output, save transport. Specify ownership, failure reporting, and which thread owns each service. Existing 2Ship symbols are examples, not required Snap names. |
| **Adopt** | Explicit factory registration and independently versioned archives | Register only resource kinds proven necessary by authoritative Snap assets; extraction→import→runtime must share one schema contract. Keep distributed original host resources separate from user-extracted game content. |
| **Adapt** | Native frame/event driver and lifecycle | Preserve Snap cooperative waits, process ordering, reset behavior, and draw completion. Baseline simulation cadence must not be driven by interpolation or monitor refresh. |
| **Adapt** | Pointer-width-aware runtime command structures | Decode fixed-width serialized addresses; relocate deliberately; use native-width pointer fields only after materialization. Audit pointer arithmetic and command indexing with the chosen ABI, not a global textual `u32` replacement. |
| **Adapt** | Software synthesis feeding a generic PCM sink | Establish Snap opcode/sample/sequence semantics first; use verified mixer behavior or a separately implemented compatible backend. Host output owns buffering/device negotiation, not game sound behavior. |
| **Adapt** | Versioned saves and shutdown joins | Preserve Snap's save semantics and add host-safe transport; no MM page table, owl/cycle split, or raw native-struct persistence. Migration is required only if a new schema is actually chosen. |
| **Reject** | Whole-port source import, `SEGMENTED_TO_K0` identity everywhere, fake busy/success APIs, disabled/dead hardware branches | They either change behavior, conceal incomplete boundaries, or presume conversions absent in Snap. Clean cutover must update every affected caller rather than retain an old unusable path. |
| **Reject** | Randomizer, enhancements, alternate-asset systems, Zelda resource/game-state abstractions, interpolation by default | They are unrelated scope and can change gameplay, saves, object ordering, and photographs. No new framework merely to resemble the reference. |
| **Reject** | Treating MIT or 2Ship's CC0 as blanket rights clearance | Licenses apply only to rights their licensors can grant; upstream decomp/vendor/Nintendo material needs its own provenance decision. |

## License applicability limits

2Ship's top-level text is CC0 1.0. It limits the affirmer's application to rights they own [Q1], does not waive trademark/patent rights, gives no title/noninfringement warranty, and expressly disclaims clearing third-party rights [Q2]. This is not evidence that Nintendo-derived source/assets or dependency code can be relicensed under 35mmIsle's MIT. MM has no project-wide LICENSE in the baseline inventory reported by the licensing owner; that absence is **not a license grant**. The references also name separate libultraship, exporter, and ZAPD submodules [B5]; their terms cannot be inferred from 2Ship's root license. Central licensing/provenance policy owns permission review, notices, dependency/tool terms, and release decisions. MIT covers 35mmIsle original work only; this document makes architectural recommendations, not legal clearance.

The authoritative Snap vendor header expressly says SGI “All Rights Reserved,” labels the source unpublished/proprietary, restricts disclosure/copying without prior written permission, and includes a Nintendo copyright notice [Q3]. This is a concrete import/release blocker for that material absent a rights-specific resolution, not merely a missing repository license.

## Proposed work-unit contracts

These are implementation boundaries for the orchestrator's Beads planning, not document task-state tracking.

| Work unit | Inputs / deliverable boundary | Observable acceptance |
|---|---|---|
| Host lifecycle + scheduler | Authoritative Snap entry/frame/reset and process/queue inventory → native lifecycle, event/input snapshots, faithful cooperative execution, explicit joins | Deterministic tick/process traces, stackful waits, orderly reset/quit; no active hardware waits whose completion source was removed. |
| Asset ABI + resources | Approved ROM/version manifest and extraction definitions → versioned serializers/importers, explicit registration, relocation/lifetime contract | Every required resource resolves with stable native references; serialized layout remains fixed-width; mismatches fail before gameplay. |
| Graphics boundary | Original Snap command/depth corpus → required renderer support and photographic surface/copy semantics | Required microcode operations and exact scoring-depth predicates pass the resolving corpus before gameplay/photo scope is accepted. |
| Audio boundary | Original Snap sequence/sample/ABI corpus → compatible synthesis + PCM sink integration | Command timing and PCM criteria hold independently of presentation FPS/device backend; reset/exit drains or cancels safely. |
| Save boundary | Original Snap save layout/checksum/error semantics → host persistence transport, and migrations only if justified | Save round-trip/corruption/interruption cases preserve valid data and report real completion/failure. |
