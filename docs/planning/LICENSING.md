# Licensing and publication boundaries

## Scope

The root `LICENSE` is canonical MIT for **original 35mmIsle contributions**: this project's original planning prose, independently authored source/glue, tools, build declarations, synthetic fixtures and documentation, where contributors hold the necessary rights. Copyright: **2026 35mmIsle contributors**. This is a provenance-scoped grant, not a license for everything referenced, cloned, generated, linked, or subsequently placed in this repository.

Nintendo/decompiled game code, ROMs, extracted or reconstructed game assets, SDK material, vendor dependencies, and upstream-derived portions are **not relicensed by that MIT grant**. Preserve upstream copyright, license, attribution, and restriction notices; record the applicable terms per file/component. Adding a 35mmIsle copyright or SPDX header, renaming a file, translating an implementation, or adapting upstream code does not erase its provenance. Mixed files require separate identification of original and upstream-derived portions; do not label the whole file MIT without evidence of permission.

**Continue native implementation with LUS and independently authored missing services.** The user's direction admits candidate-scoped original runtime work, the pinned MIT LUS integration and lawful private ROM extraction/reference/capture development under [ADMISSION](../development/ADMISSION.md). Restricted SDK implementations are excluded and replaced, not prerequisites to obtain before engineering can proceed. This is authorization for the requested private development use, not a third-party redistribution grant or blanket MIT determination. Do not publish ROMs, extracted assets, copied decompiled/SDK payloads, reference checkouts, generated game archives, compiled game payloads, or secrets. Actual source imports and release artifacts retain the separate reviews below.

## Reuse decisions

| Decision | Boundary |
|---|---|
| **Adopt** | Original 35mmIsle work under MIT; pin-qualified research citations; upstream notices without alteration; separately reviewed permissive dependencies such as LUS, retaining their own identities. |
| **Adapt** | Architectural ideas, interface requirements, and independently authored glue. Any copied/adapted source remains an upstream-derived candidate requiring an import decision, even if only a short fragment or translated form. |
| **Reject** | Blanket MIT relabeling; wholesale Snap/Ghostship/Zelda imports based on root metadata; proprietary SDK copying; ROM/asset/archive redistribution; treating private-use authorization, extraction, ownership, or CC0 as a third-party redistribution grant. |

The prior whole-roadmap external-permission stop is historical and superseded: `bd_35mmIsle-v4u.1.3` is no longer a global W00 dependency. I1/I2 apply to the actual proposed material and use; they do not require permission to copy an excluded SDK before an original replacement, MIT LUS integration or admitted private ROM research can proceed.

### Attribution inventory requirements

Before an import or release, a record must identify **component and destination paths; original/derived/generated category; source owner/repository/full commit/path/span; version and content hash; copyright holders; exact license text/notices and scope; modifications; transitive dependencies and embedded data; source/binary distribution and linkage; required attributions/source offers or other obligations; reviewer decision and evidence**. Record missing grants explicitly as unresolved. SPDX identifiers may summarize an established determination; they cannot establish it. Keep original MIT and upstream notices separate, and deliver applicable third-party notices with shipped copies, not only an online link.

## Private ROM-based validation strategy

The user confirms a lawful private development ROM and directs extraction, reference/rebuild research and comparison capture for this port. [ADMISSION](../development/ADMISSION.md) records the supplied identity/size evidence and this private-use authorization. This is not an acquisition service, a legal-clearance opinion, a license to import restricted SDK source, or permission to redistribute third-party material. No additional blanket SDK permission is a prerequisite to that admitted work.

- Authorized developers provide their own lawfully obtained supported ROM in a private, access-controlled workspace outside the public checkout. No ROM download links, acquisition service, or public CI secret containing a ROM. Check expected identity locally; Snap's upstream README provides the US SHA-1, but a matching hash proves version identity only.
- Run extraction, reference rebuilds, game-driven development/tests and comparison capture within that private environment using the admitted lawful input. Keep ROM-derived assets, archives (`.otr`/`.o2r` or other formats), reconstructed binaries, screenshots/audio, dumps, save data and logs private. Restricted SDK source is not copied into the native port; each actual imported component retains its own provenance and terms. No shared/public CI cache, automatic artifact upload or committed ROM-derived fixture.
- Public CI may exercise original runtime/glue with independently created synthetic fixtures and permissively licensed dependencies. Synthetic means independently created, not game data renamed or reformatted. Game fidelity claims need separately recorded private reference evidence; synthetic tests do not prove fidelity.
- Publish only reviewed non-payload summaries: source/ROM version identifiers, test configuration, aggregate pass/fail and approved non-reconstructive measurements. Memory dumps, instruction/data traces, visual/audio captures, identifiers containing secrets, and local paths require review before disclosure. Retention/access rules apply to private outputs as well.
- User-side extraction development may proceed with authorized input and no bundled game content. Any proposed public extractor/runtime/metadata package needs its own composition review; private extraction neither grants rights to publish generated contents nor requires a blanket future-game-source permission before implementation.

## Acceptance constraints

The license text remains canonical MIT with the stated copyright. Applicability stays tied to provenance, not repository location. Every one of the seven pins has an evidence-backed disposition; narrower grants and proprietary notices remain visible. Missing permission blocks the affected actual import/release, not all native engineering or admitted private ROM work. Public records contain no protected payloads or secrets. Import/release review must resolve actual component and artifact composition; private-use authorization does not bypass redistribution review. The historical licensing research performed no builds, runtime tests, publication gates, commits or pushes and asserted no legal clearance; this correction adds no runtime or full-game qualification claim.
