# Shipwright and Ocarina of Time: transferable port boundaries

## Scope

Source-level comparison for 35mmIsle planning only: lifecycle/scheduling, named resources and extraction, address/Gfx ABI, framebuffer/depth access, software audio to PCM, save evolution, and native packaging. No implementation, source imports, enhancement work, randomizer, interpolation feature, or UI-framework adoption is authorized by this study. All adoption decisions below concern **patterns**, not permission to copy their implementations.

### Resource and ABI contract

**Proposed invariants:** a serialized resource never contains a host pointer; resource IDs are stable across relocation; segment tokens are resolved through a game-aware boundary; a resource's owner outlives every game/render/audio reference to its returned data. Primitive resource support does not imply support for Snap models, animations, collision or audio banks.

**Central integration evidence, not an additional experiment by this study:** the frozen authoritative-Snap inventory records a directly reviewed pointer-mask defect in [src/sys/ml.c:11–17](https://github.com/ethteck/pokemonsnap/blob/df8815e75f3d79618466e01e0827c6165b93d11c/src/sys/ml.c#L11-L17): a 32-bit complement mask clears upper host-pointer bits even when surrounding arithmetic uses `uintptr_t`. The orchestrator's isolated compiled 64-bit smoke demonstrated truncation with both synthetic and real allocated addresses; this is not a native-game runtime result. Before the resource/photo cutover, resolve typed pointer payloads, host heap/overlay sizing and serialized/native structure separation rather than relying on superficial cast replacement. The inventory is signature-scoped evidence, not an all-file correctness audit or a blocker count; its full results remain centrally owned.

Shipwright's `ResourceMgr_OTRSigCheck` checks alignment/null and then reads seven bytes at a supplied pointer [R2]. **Reject as a general address validator:** this does not prove the pointer is mapped or sufficiently long. A Snap design must distinguish known resource handles, valid host pointers and segmented addresses before any signature dereference. Preserve the frontend naming convention only if required by the pinned renderer; do not make arbitrary pointer sniffing the ABI contract.

The factory pattern is stronger than a raw ROM-to-struct cast, but not every factory is generic: `ArrayFactory` handles vertices and only two scalar types in its switch [R4]. Adopt only a measured primitive subset and create Snap-specific schemas where reconstruction is necessary; reject room, scene, skeleton and OOT soundfont factories as default game abstractions [R3].

The ROM validator's 32/54/64 MiB allowlist, OOT version codes and MQ debug header exception are game-specific [R5]. They must not leak into Snap support. **Proposed:** verify authoritative Snap revision and byte order before extraction; record the normalized input digest, extractor revision and resource-schema version in an output manifest; require the runtime to reject incompatible archives. This adds no claim that Torch presently supports Snap or that input ownership grants redistribution rights.

### Photo/readback contract

**Proposed acceptance requirement, informed by the authoritative-Snap/validation workstream:** scoring must receive CPU-visible 64×48 `u16` depth buffers with sentinel `0xFFFC` and the required current/per-Pokémon/pre-Pokémon equality semantics. A successful color readback or a plausible photo is not a substitute.

[F3] demonstrates an explicit CPU **color** readback command, center cropping, byte-order control and render-state restoration. It does not establish when the destination becomes CPU-readable, whether hidden coverage/depth bits survive, or how a full depth image is exported. [F2] proves a game-callsite adaptation for isolated depth samples, not bulk readback correctness. **[INFERENCE]** repeatedly querying all pixels could still produce the wrong values/frame and undesirable synchronization cost; no implementation should choose that route without measurement.

Keep the scoring pass at authoritative game dimensions and frame identity, independent of host resolution/aspect ratio. The OOT 320×240 crop is a candidate for display/thumbnail handling only; reject it as a scoring-buffer conversion. A presentation-only frame must never duplicate a capture/scoring side effect. This borrows the once-per-game-frame distinction in [F3], not Shipwright's interpolation implementation.

### Audio and save contract

The audio path has three separate obligations: **game sequencing/loading → synthesis/microcode semantics → host PCM queue** [A1–A4]. Preserve Snap's sequencing and supported `libaudio` command semantics; specify signedness, channels, sample rate, sample-count units and PCM buffer ownership at the sink. Shipwright's 32 kHz setup and 528/560 occupancy-controlled batches are observed OOT settings, not an approved Snap timing model [R3][A4]. Its mixer has one static state block [A3]; do not assume reentrancy, independent parallel mixers or safe reset concurrency. Custom streamed music/codec extensions are excluded.

For saves, version the serialization independently of compiler layout, host pointer width, configuration and application version. Historical migration must parse an explicitly described old layout and preserve its source until a verified replacement is committed. Shipwright's unconditional old-file rename after conversion, unsupported-version assertions and section-skipping policies are not adopted [S2][S3]. Its desktop path writes/flushes/syncs a temporary file then renames; Switch/Wii U instead remove/copy [S3]. **[INFERENCE]** those differences, and the absence of a parent-directory synchronization step in the cited routine, preclude claiming universal crash/power-loss durability. Snap photo/album bytes require their own fidelity checks; OOT inventory migration does not cover them.

## Licensing and limits of proof

Observed local filename/root inspection found **no project-wide LICENSE** in either pinned Shipwright or OOT tree. That is a bounded inspection finding, not a legal conclusion that every file has identical terms. Shipwright's README establishes dependency on decompiled OOT and a user-supplied game copy [P1]; it is not a permissive license. The found MIT notice explicitly describes OoT-Randomizer-derived code in `3drando` [P2]; it does **not** license the native port, game decomp, mixer, generated names, extracted data or vendor code as a whole. The mixer headers/source spans inspected contain no grant [A3]; copying requires file-specific provenance and rights review.

**Handoff to central licensing owner:** keep all listed implementations reference-only until the owner resolves the exact files and applicable terms; do not characterize Shipwright/OOT as MIT. Central findings additionally identify proprietary SGI/Nintendo notices in authoritative Snap and distinct terms in OOT tools; those are independent blockers, not cured by local extraction or an original-work MIT license. 35mmIsle's MIT grant can cover original planning/adapter work where the author has rights; it cannot relicense Nintendo, decomp, vendor or unlicensed upstream material. No legal clearance is asserted here.

Evidence proves that these reference boundaries exist in source. It does not prove they compile against the independently selected LUS revision, execute Snap custom microcode, reproduce N64 depth or audio, migrate Snap saves, meet frame-time goals, support all advertised platforms, or are cleared for reuse/distribution. Those outcomes require the resolving experiments and provenance decisions above; none was exercised during planning.
